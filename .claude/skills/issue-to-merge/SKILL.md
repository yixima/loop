# issue-to-merge — 外側のループ

課題ファイルを受け取り、**停止条件を満たすまで**自動で工程を回します。
従来は人間が回していた「次に何をやるか」の一番外側の輪を、このスキルが担います。

## 入力

- 課題ファイル: `docs/issues/NNNN-slug.md`（引数で指定。省略時は `状態: open` のものから最も優先度の高いものを選ぶ）

## 停止条件（これ以外で止まらない・これ以外を「完了」と呼ばない）

**成功で停止:**
- 課題ファイルの受け入れ条件がすべて満たされている
- `./scripts/verify.sh` が終了コード 0
- GPT レビューの blocker が 0 件

**失敗で停止（人間に引き渡す）:**
- 実装フェーズで verify が **5回** 通らなかった
- レビュー指摘の反映を **3周** しても blocker が消えない
- 要件・設計に未確定事項が残っている
- 破壊的操作、スコープ外の変更、認証情報の扱いが必要になった

**時間・回数の上限に達したら、成功と偽らずに「未完了」として報告して止まること。**

## 手順

### 0. 準備

```bash
git status --short --branch
./scripts/verify.sh --quick   # 開始時点の状態を記録（既に赤いなら、それは今回の変更のせいではない）
```

課題ファイルを読み、`ISSUE_ID` を確定する。作業ブランチが未作成なら作る。

### 1. 設計フェーズ — `architect` サブエージェント

Task ツールで `architect` サブエージェントを起動し、課題ファイルのパスを渡す。

生成物:
- `docs/requirements/<ISSUE_ID>.md`
- `docs/design/<ISSUE_ID>.md`
- `docs/plans/<ISSUE_ID>.md`

**ゲート:** 未確定事項が1件でも残っていたら、実装へ進まず、質問を列挙して **人間に確認して停止**。
ここで推測して進むと、間違った方向へ高速に突き進むシステムになります。

**人間の関与ポイント①**: 設計書を人間が斜め読みする工程です。
`docs/design/<ISSUE_ID>.md` のパスと設計の要点3行を必ず提示してください。

### 2. 実装フェーズ — `implementer` サブエージェント

実装計画書の「並行実行できるタスク」を見て、依存のないタスクは **複数の implementer を同時に起動** して手分けさせる。
依存があるものは直列に実行する。

各 implementer には必ず次を渡す:
- `docs/design/<ISSUE_ID>.md` と `docs/plans/<ISSUE_ID>.md` のパス
- 担当するタスク番号
- 「テストを先に書く」「テストを消して緑にしない」「verify が通るまで完了と呼ばない」

### 3. 検証フェーズ

```bash
./scripts/verify.sh
```

- 終了コード 0 → 次へ
- 0 以外 → 失敗内容を implementer に返して修正させる。**カウンタを +1**。
- カウンタが 5 に達したら **停止**。何を試して何が分かったかを報告する。

実装計画書の「verify 実行回数」を毎回更新すること（これが再開時の外部記憶になる）。

### 4. レビューフェーズ — `reviewer` サブエージェント

`reviewer` サブエージェントを起動する。reviewer は内部で必ず次を実行する:

```bash
ISSUE_ID=<ISSUE_ID> ./scripts/gpt-review.sh
```

- **自分（Claude）の判断だけで合格にしない。** 開発元の異なる GPT 系モデルの採点が必須。
- `gpt-review.sh` が **終了コード 4** を返した場合は、サンドボックスの制約であって未認証ではない。
  サンドボックスを無効にして再実行する許可を人間に求める。誤診断でレビューを飛ばさないこと。
- `gpt-review.sh` が **終了コード 3** を返した場合は本当に未認証。**レビューを飛ばさずに停止**し、
  「Codex CLI の認証が必要です」と人間に伝える。

blocker があれば implementer に修正させ、**ステップ3（検証）から**やり直す。
このレビュー往復は最大 3周。3周で blocker が消えなければ停止して報告。

### 5. 仕上げ

- 実装計画書のチェックボックスをすべて更新し、作業ログを書く
- `git add` して、課題IDを含む説明的なコミットメッセージでコミット
- `git push -u origin <branch>`

### 6. 報告

以下のフォーマットで人間に報告する。

```
■ 課題: <ISSUE_ID> <タイトル>
■ 結果: 完了 / 未完了（理由）

受け入れ条件:
  [x] ...
  [ ] ...（未達なら理由）

verify:  終了コード 0（テスト N件通過 / lint 0件）  試行 M/5 回
レビュー: GPT(<model>) blocker 0件 / major N件（対応済み/見送り）
差分:    N files changed, +X / -Y
ドキュメント: docs/requirements|design|plans/<ISSUE_ID>.md

■ 人間の判断が必要なこと:
  - 本番反映のタイミング（このループには含めていません）
  - <その他>
```

## このループがやらないこと

- **本番反映（デプロイ）**: 意図的に自動化していません。システム上は反映できても業務都合で触れない時があるため、
  ここは人間が判断する工程として残しています。
- **課題の起票**: 何を作るかを決めるのは人間の仕事です。
- **原則（CLAUDE.md）の書き換え**: 判断基準を自分で緩めることは禁止です。

## 覚えておくこと

AIの「できました」は事実ではなく、ただの主張です。
テスト結果という証拠が揃うまで、完了として扱ってはいけません。
