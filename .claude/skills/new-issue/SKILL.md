# new-issue — 課題ファイルを起票する

ループの品質は入り口の課題ファイルで決まります。ここが曖昧だと、AIは高速に間違った方向へ進みます。

## 手順

1. `docs/issues/` の既存ファイルを見て、次の連番を決める（`0001`, `0002`, ...）。
2. `docs/templates/issue.md` を雛形に `docs/issues/NNNN-slug.md` を作る。
3. 人間の説明を、テンプレートの各項目に振り分ける。
4. **受け入れ条件を機械判定できる形に書き換える。** ここが最重要。
5. 埋められない項目は勝手に埋めず、人間に質問する。

## 受け入れ条件の書き換え例

| 人間の言葉 | 機械判定できる受け入れ条件 |
|---|---|
| 「ログイン機能がほしい」 | `POST /login` が正しい資格情報で 200 と JWT を返す / 誤った資格情報で 401 を返す / レスポンスにパスワードハッシュを含まない |
| 「速くしたい」 | 1万件の入力に対する処理が 500ms 以内で完了するテストが通る |
| 「見やすくして」 | （機械判定できないので人間の目視確認が必要。その旨を明記し、確認手順を書く） |

機械判定できないものを、できるフリで書かないこと。
できないなら「人間の目視確認が必要」と明記する方が、ループは正しく止まります。

## 受け入れ条件どうしの矛盾を検算する

**書き終えたら、受け入れ条件を1つずつ突き合わせて、同時に満たせるかを確かめること。**
1つ1つは正しいのに、2つ並べると両立しない、という書き方が一番よく起きる失敗です。
これを残したまま実装に流すと、設計フェーズで止まるか、最悪「たまたま今は通る」実装ができあがります。

特に多いのが **「挙動を変える」と「後方互換」の同居** です。

| 危険な組み合わせ | なぜ両立しないか |
|---|---|
| 「省略時は現在時刻を使う」＋「既存テストを1件も変更せず通す」 | 既存テストは固定の戻り値を期待している。時刻で変わるなら通り続けられない |
| 「新しい既定値にする」＋「既存の呼び出し側は変更不要でこれまでどおり」 | 既定値を変えた時点で「これまでどおり」ではない |
| 「エラーを送出する」＋「既存の戻り値を維持する」 | 同じ入力に対してどちらかしか起きない |

見つけたときは、**どちらが課題の目的か**に立ち返って一方を取り下げます。
背景に書かれた「なぜやるのか」が判定基準です。目的そのものを打ち消す条件のほうが誤りです。

取り下げた条件は消すのではなく、**なぜ取り下げたかを書き添えて残す**こと。
そうしないと、次に読んだ人が良かれと思って書き戻します。

## テストの扱いを明示する

「既存テストを変更しない」と書く場合は、**それが本当に可能か**を確かめてから書くこと。
既存テストの更新が避けられないなら、次のように書き分けます。

- ✅ 「実時刻に依存しないよう引数を明示する形に更新してよい。件数は減らさない」
- ❌ 「既存テストは1件も変更しない」（更新が必要な場合、AIは止まるしかなくなる）

いずれの場合も、**削除・スキップ・アサーションの緩和は禁止**と明記すること。

## 必ず埋める項目

- **背景**: なぜやるのか。ここが薄いと、AIは正しいゴール条件を自分で設計できません。
  ループエンジニアリングの肝は、正しいコンテキストが共有されていればAIが必要な機能とテストを
  自分で設計できる、という点にあります。背景は削らないこと。
- **スコープ外**: やらないことの明示。スコープクリープを止める柵になります。
- **停止条件**: 何回試して駄目なら止まるか。既定は「5回試して駄目なら報告して停止」。

## 最後に

作った課題ファイルのパスを提示し、
「`/issue-to-merge <ISSUE_ID>` でループを回せます」と案内する。
