# ループエンジニアリングとは（記事の手法まとめ）

出典: 根岸智幸「「Claude Code×GPT」自律ループが凄すぎ、仕事が"3つ"に減る5ステップ」
ビジネス+IT, 2026-08-21 — <https://www.sbbit.jp/article/cont1/186558>

## 発端

2026年6月7日、OpenClaw 作者の Peter Steinberger 氏が X に投稿した持論が起点になった。

> もうコーディングエージェントにプロンプトを書くべきではない。エージェントをプロンプトするループを設計するべきだ。

Claude Code の開発を率いる Boris Cherny 氏の「私の仕事はループを書くことだ」という発言も拡散し、
6月末に Anthropic が公式ブログでこの考え方を「ループエンジニアリング」として定義した。

Anthropic の定義: **ループとは「停止条件が満たされるまでエージェントが作業サイクルを繰り返すこと」**。

## 従来との違い

| | バイブコーディング | ループエンジニアリング |
|---|---|---|
| 一番外側の輪（次に何をやるか） | **人間**が手動で回す | **機械**に任せる |
| 人間の役割 | 指示 → 確認 → また指示 の操作員 | ゴールを決めて例外だけ対応する監督 |
| 人間が時間をかける場所 | 何と頼むか | いつ動かし、どう検証し、いつ止めるか |

AIとの関わり方は段階を追って外側へ移動してきた。

1. **プロンプトエンジニアリング** — 何と頼むか
2. **コンテキストエンジニアリング** — 何を知らせるか
3. **ハーネスエンジニアリング** — どんな道具を使わせるか（実行環境の整備）
4. **ループエンジニアリング** — いつ動かし、どう検証し、いつ止めるか ← いまここ

プロンプトが不要になるわけではない。ループの内部では今もプロンプトが働いている。
変わるのは、エンジニアが最も時間をかける場所だけ。

## 記事の筆者の環境

中心は Claude Code。

- **CLAUDE.md** に開発の原則を明文化（「最小の実装から始める」「仕様を推測せず、必ず検証する」「基盤部分に仮のデータを使わない」など、AIが迷ったときの判断基準）
- **要件定義書・設計書・実装計画書** の名称と役割を決め、AIに必ず作らせ、参照させる。これらが **AIの外部記憶** として働く
- **サブエージェント**を仕事別に用意（設計担当／テストしながら実装する担当／レビュー担当）。
  レビューは **開発元の違う GPT 系モデル** に任せ、作った本人に採点させない
- 仕上げが **`/issue-to-merge`** という自作スキル。課題ファイルを読み、実装計画を立て、複数のAIが手分けして実装し、
  GPTのレビューを受け、テストと本番反映と動作確認を済ませ、完成したコードを本体に組み込むところまで自動で進む

約1年運用した結果、筆者の仕事は次の3つに絞られた。

1. 設計書を斜め読みして、問題に気がついたら指摘する
2. 長い開発をどこで区切るか決める
3. 本番反映のタイミングを判断する

## 成功に導く5ステップ

多くの人は最初に「全自動で回るコマンド」を作りたがるが、**順番は逆**。
判断の原則と検証の仕組みがない状態で自動化すると、**間違った方向へ高速で突き進むシステム**ができあがる。

| Step | 内容 | このリポジトリでの実体 |
|---|---|---|
| **1** | **判断の原則を書く** — CLAUDE.md のような設定ファイルに「迷ったときのルール」を10〜20個 | `CLAUDE.md`（21項目） |
| **2** | **文書をAIの外部記憶にする** — 要件定義書・設計書・実装計画書の3点を毎回作る決まりにする | `docs/templates/` と `docs/requirements|design|plans/` |
| **3** | **作る係と評価する係を分ける** — 自分の宿題を自分で採点させない | `.claude/agents/{architect,implementer,reviewer}.md` と `scripts/gpt-review.sh` |
| **4** | **合格を機械が判定できるようにする** — テストや文法チェックをコマンド一発で | `scripts/verify.sh` |
| **5** | **繰り返す作業を標準手順書にする** — 頻出作業をスキルとして登録 | `.claude/skills/` |
| **最後** | **外側のループをつなぐ** — 部品が揃っていればAI自身に書かせられる | `.claude/skills/issue-to-merge/` と `scripts/loop.sh` |

## 「終わり」の定義が肝

- **悪いゴール**: 「ログイン機能を完成させろ」
  → 抽象的すぎる。AIが「できました」と言えば終わってしまう。
- **良いゴール**: 「テスト42件がすべて通り、文法チェックのエラーが0件になるまで修正する。5回試して駄目なら、状況を報告して止まる」
  → AIは正しく動く。

ただし、そんな指示は人間には面倒すぎる。
ここで **コンテキストエンジニアリング** が効いてくる。正しいコンテキスト（詳しい目的や背景事情）が共有されていれば、
「ログイン機能を完成」に必要な機能とテストをAIが自分で設計し、実装からレビューまで完遂できる。
必要十分なゴール条件も自分で設定させ、完了したか自分でチェックさせる。
**このゴール判定の精度こそがループエンジニアリングの肝**。

## 人間の関与を設計する

完全無人化は目標ではない。記事の筆者も **本番反映の直前だけは自分で判断する** と決めている。
システム上は反映できる状態でも、業務の都合で触れないときがあるから。

> 人間をどの工程から外し、どこに残すか。それを決めること自体がループエンジニアリングなのだ。

このリポジトリでは、人間の関与ポイントを次の3つに置いている。

1. 課題の起票（何を作るかを決める）
2. 設計書の斜め読み（`architect` の出力後、`implementer` に渡す前）
3. 本番反映の判断（`issue-to-merge` にデプロイを含めていない）

## 冷静な数字

- 2026年7月末にマイクロソフトなどが公開したベンチマーク **LoopsBench**（112件の長時間開発タスク）では、
  当時最強の **Claude Opus 4.7 + Claude Code の組み合わせでも完全解決率は 25%**。
  実際の GitHub 上の複雑な連続タスクに限れば **成功率は 3%台**。
- 優秀なモデルを無限に回せばソフトウェアが勝手に完成する、という期待は現時点では幻想。

ループエンジニアリングの本当の姿は、こう表現できる。

> **失敗するAIを前提に、失敗を検出し、修正させ、再試行させ、それでも駄目なら安全に止める。
> そのための制御の仕組みを作る技術。**

2026年7月公開の査読前論文 **「Proof-or-Stop」** も同じ思想を示した。

> AIの「終わりました」は事実ではなく、ただの主張である。
> テスト結果という証拠がそろうまで、完了として扱ってはならない。

この考え方は `CLAUDE.md` の原則7〜9、`verify.sh` の終了コード、`loop.sh` の試行上限として実装してある。

## コスト

ループ化するとAIの利用料は増える。Anthropic は **定型作業には安価なモデルを、重要な判断には高性能なモデルを**
充てるよう推奨している（「ハイローMIX」）。
このリポジトリでは `.claude/agents/*.md` の `model:` 行で役割ごとにモデルを指定できる。
定型的な整形やファイル移動しかしないサブエージェントを追加する場合は、そこを `haiku` に落とすとよい。

## 残る人間の仕事

コンテキストを整え、ゴール条件を定義し、どこで人間が引き取るかを決める。
AIを安全に自動運転させるための高度な判断と設計が、人間の仕事になる。
経験による勘だけでは足りず、ソフトウェア工学・組織マネジメント・認知心理学といった基礎知識が効いてくる領域。
