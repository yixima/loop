# 課題: verify.sh がテストの弱体化を検出できるようにする

- **ID**: `0003-verify-detect-test-tampering`
- **起票日**: 2026-08-25
- **優先度**: high
- **状態**: open

> 課題 `0001-greeting-time-of-day` のレビュー3周目で、別ベンダーのモデル（Codex/GPT）が blocker として指摘した欠陥です。
> 0001 の制約（対象ファイルは `src/loopdemo/greeting.py` と `tests/` のみ）の外にあるため、
> 人間の判断により別課題として切り出しました（2026-08-25）。

## 背景（なぜやるのか）

`scripts/verify.sh` はこのリポジトリの**唯一の停止条件**である。
しかし現在の verify.sh は「テストが通ったか」しか見ておらず、**テストそのものが骨抜きにされていないか**を一切検査しない。

実測（0001 のループ中に確認）:

```
既存テストのアサーション2件を self.assertTrue(True) に置換した状態で
$ ./scripts/verify.sh
→ 終了コード 0（合格）
```

つまり、エージェントがテストを弱体化させて緑にしても、verify.sh は合格を返す。
CLAUDE.md 原則9（テストを消して緑にしない）は文章として書かれているだけで、機械的な担保がない。

停止条件が改ざんを検出できないなら、**このリポジトリの他のすべての「合格」判定が信用できなくなる**。
これが優先度 high の理由である。

なお 0001 では、この検査を受け入れ条件 F11
（「既存テストの変更は許可された2行のみ」）として文章で書いたが、
**機械が判定できない形で書いたことが問題の本質だった**。
「増減行数が4行であること」という代替のチェックも、何行変わったかしか見ておらず、どの行が変わったかを見ていない。
同じ誤りを繰り返さないため、この課題の受け入れ条件はすべて grep と git diff で判定できる形に落とすこと。

## ゴール（何が達成されたら終わりか）

テストを弱体化させて緑にしようとしたとき、`./scripts/verify.sh` が人間の介在なしに FAIL する状態。
また、既存テストファイルに変更があったとき、その差分が verify.sh の出力に必ず現れ、人間が見落とせない状態。

## 受け入れ条件（機械が判定できる形で）

- [ ] `tests/` 配下に自明に真なアサーション（`assertTrue(True)` / `assertFalse(False)` / `assert True` /
      本体が `pass` のみのテストメソッド）が1つでも存在すると `./scripts/verify.sh` が**終了コード 0 以外**で終わる
- [ ] 上記の検査は verify.sh のチェック一覧に独立した項目として現れる（例: `py:test-integrity`）。
      既存の `run` / `skip` の枠組みに合わせること
- [ ] 検証手順: `tests/` の任意のテストメソッド本体を `self.assertTrue(True)` に置換した状態で
      `./scripts/verify.sh` を実行し、終了コード 0 以外になることを実測する。置換は必ず元に戻すこと
- [ ] 上記の改ざんがない現在の `tests/`（`test_greeting.py` / `test_greeting_time_of_day.py`）に対しては
      `./scripts/verify.sh` が**終了コード 0** で完了する（誤検出しない）
- [ ] `tests/` 配下に既定ブランチとの差分があるとき、`./scripts/verify.sh` の標準出力にその差分が含まれる。
      判定方法: `./scripts/verify.sh 2>&1 | grep -c '^[+-].*assert'` が 1 以上を返す
- [ ] `tests/` 配下に差分がないときは、差分出力は空でよい（この場合も終了コード 0）
- [ ] 差分の比較基準は `git merge-base` を用いること。素の `git diff` は working tree と index の比較のため、
      `git add` 済み・コミット済みだと常に空を返し、検出機構が無言で死ぬ（0001 で実際に踏んだ罠）
- [ ] `./scripts/verify.sh --quick` でも上記の整合性検査が動く（テストだけ通せば済む抜け道を作らない）
- [ ] `./scripts/verify.sh` が終了コード 0 で完了する

## スコープ外（やらないこと）

- 既存テスト（`tests/test_greeting.py` / `tests/test_greeting_time_of_day.py`）の変更
- `src/` 配下の変更
- カバレッジ計測の導入（別の話。この課題は「テストが空回りしていないか」だけを見る）
- 変異テスト（mutation testing）ツールの導入（有用だが重い。必要なら別課題）
- CI の追加
- 課題 `0002` のフォールバック修正（別課題として起票済み）

## 制約・前提

- 対象ファイルは `scripts/verify.sh` のみ（必要なら検査用スクリプトを `scripts/` に追加してよい）
- **検査を緩めて緑にしてはいけない。** 誤検出が出た場合、閾値を下げる前に、
  なぜ検出されたのかを特定して報告すること（CLAUDE.md 原則9・10）
- 検出パターンは正規表現で表現し、verify.sh 内に直接書くこと。外部依存（新しい pip パッケージ）を増やさない
- 既定ブランチ名をハードコードしないこと（`git merge-base` で解決する）

## 停止条件

- 受け入れ条件をすべて満たし `./scripts/verify.sh` が通ったら完了。
- 修正を **5回** 試して通らなければ、状況を報告して停止する。
- 判断に迷う仕様変更が必要になったら、実装せず質問して停止する。
